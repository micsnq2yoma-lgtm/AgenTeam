# 方案：主动提醒与规则学习、跨 Agent 共享画像

> 日期：2026-11-22。状态：**待用户确认，确认前不开发。** 这两项是最初对比 Linger 时划出的剩余部分，都会触及新的状态 owner 或事件来源，按根 `CLAUDE.md` 须先讨论架构。已完成的部分见 `assistant_profile.md`。

## 一、主动提醒与规则学习

### Linger 怎么做

对每个事件（邮件、日历变化、Slack 提及、与助理的聊天窗口）做四选一：**马上告诉**、**先帮你准备**、**稍后跟进**（只记录，到点再查）、**不打扰**；有克制规则（夜间只记录、每天提醒上限、聊天安静 3 分钟后才发）。每晚读自己主动发出的每条消息及之后的 20 条回复，把"下次直接告诉我""这种别提醒"沉淀成线索，同类线索出现两次、或用户直接点明类别，就升级成规则（如"供应商发票 → 马上告诉"）。规则只是一张短清单，不重新训练。

### 我们已有什么

| 需要的能力 | 现有 owner |
|---|---|
| 周期性主动唤醒 | IM Heartbeat（间隔、活跃时段、无事回复 `HEARTBEAT_OK` 即静默） |
| 便宜的预判 | 命令 Detector 型 Task：先跑本地命令，`quiet` 不唤醒 AI，`activate` 才交给 AI |
| 夜间整理 | 托管 Task（Gardener、Molt 的模式） |
| 触达用户 | Task 通知、IM 私聊目标、桌面通知 |
| 读历史 | `myagents session get/list` |

没有的：邮箱、日历、Slack 这类外部事件源。产品里没有内置连接器，只能经用户自己配置的 MCP 工具获得。

### 建议的做法（不新增状态 owner）

1. **规则放在工作区文件 `PROACTIVE_RULES.md`**，和 `03-USER.md` 一样是用户可读可改的文件，分"规则"和"线索"两节、每条带出处和日期。规则被读到时才生效；用户随时可以直接改或删。
2. **判断复用 Heartbeat 和 Detector**：Heartbeat 的提示词里加入四选一的判断流程和克制规则（夜间不推、每天上限、同一事项一天只判一次），读取 `PROACTIVE_RULES.md`；有确定性信号的事项（例如某个文件夹出现新文件）用 Detector Task 预判。
3. **学习用一个新的托管 Task**（和 Gardener 同模式）：每晚读最近主动发出的消息及之后的用户回复，按固定表把回复归为线索或规则（"下次直接告诉我"→ 马上告诉；"这个别提醒"→ 不打扰；"现在别提醒但继续跟踪"→ 稍后跟进；赞同、"好的"或没有回复 → 不记），写入 `PROACTIVE_RULES.md`，写入走 `section_edit.py`。
4. **事件源先用已有的**：IM 消息、Task 与 Goal 结果、Record 录音转写，外加用户已配置的 MCP 工具。邮箱、日历等待有通用连接器再接，不在本期做。

### 风险与取舍

- **打扰成本高于漏提醒**：默认保守，新用户默认不主动推送，须在设置里显式开启；首次开启给出夜间时段和每日上限的默认值。
- **规则学习会学错**：线索需要同类出现两次才升级；每次升级在下一次主动消息里附一句"我现在会这样处理 X，说一声就改"，让用户能纠正。
- **隐私**：学习 Task 读的是助理自己发出的消息和用户的回复，只留下规则，不复制消息原文进 `PROACTIVE_RULES.md`。
- **能验证到什么程度**：判断质量只能靠真实使用观察，自动化测试只能覆盖规则文件的读写、克制规则和线索升级的确定性部分。

### 需要你确认

1. 是否按"规则放工作区文件、复用 Heartbeat 和 Detector、一个新托管 Task 学习"的方向做？
2. 默认关闭、显式开启，是否接受？
3. 第一期只用已有事件源（IM、Task 结果、录音），不做邮箱和日历，是否接受？

## 二、跨 Agent 共享画像

### 要解决的问题

用户有多个助理（或多个工作区的 Agent）时，每个都有自己的 `03-USER.md`，告诉一个助理的内容，其他助理不知道。

### 选项

| 方案 | 做法 | 权威数据在哪 | 新增什么 | 主要代价 |
|---|---|---|---|---|
| **A. 指定一个主画像** | 把某个助理的工作区标为"画像主人"，其他助理的 USER 章节由 App 以只读文件的形式同步过去 | 主助理的工作区文件 | 一个"主画像"设置，加一个单向同步（Rust，文件复制） | 同步时机和冲突（目标文件被手改）要处理；主助理被删、移动时要处理 |
| **B. App 级画像文件** | `~/.agenteam/user-profile/USER.md` 作为唯一权威，Rust 持有；各工作区的 `03-USER.md` 变成它的只读投影 | App 数据目录 | **新的状态 owner**（Store、锁、广播）和投影机制 | 改动最大；已有工作区的 USER 文件要迁移 |
| **C. 不共享，只提供一键复制** | 用户在设置里选"把这个助理的画像复制到另一个助理" | 各自的工作区 | 一个一次性的复制命令 | 不是真正共享，之后会各自演化 |

### 我的建议

选 **A 的最小版本**：只做"主画像 → 其他助理"的单向同步，且只同步固定章节里属于画像的几章（背景、沟通风格、工作方式、偏好、写作风格），**不同步"基本信息"和"近期观察"**，因为后两者是各助理自己的称呼和日常观察。理由：权威数据仍是工作区文件，不引入新的持久化 owner；单向同步没有合并冲突；B 的收益（真正的单一权威）在只有少数助理时抵不上迁移成本。如果你以后希望所有助理读同一份画像，再升级到 B，A 里的章节分工可以直接沿用。

**需要新的东西**：同步由谁触发（画像 Task 或 Gardener 写完后通知，还是启动与周期对账）、目标文件被手改时的处理（以主画像为准并保留旧版备份，还是提示用户）。这两点需要你定。

### 需要你确认

1. 选 A、B 还是 C？
2. A 的话：同步哪几章（我的建议如上）、冲突时以主画像为准并保留备份是否接受？
3. 哪个助理是主画像：默认取最早创建的助理，还是在设置里手动指定？
