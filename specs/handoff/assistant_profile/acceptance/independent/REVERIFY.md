## 发现的缺陷与偏差

| 编号 | 严重程度 | 复现与实际结果 |
|---|---|---|
| N1 过期锁回收仍会丢写 | 高 | 在相同基线文件旁放置修改时间为两分钟前的 `.USER.md.lock`，同时启动两个原版写入进程。应只有一个成功，实测两个均退出 0，最终只保留一笔。扩大到五个进程时首轮有三笔报告成功，最终仍只保留一笔。源码中判定过期和删除锁是两个操作，存在删除另一进程新锁的窗口。 |
| N2 画像 Task 的桌面汇报时机不稳定 | 中 | 在新 DeepSeek 助理提交简历和网址，等待画像 Task 完成。首次回复已查 Task 并总结，但未说明桌面汇报时机。下一条普通用户消息没有主动查 Task，也没有画像完成摘要。直接询问会汇报画像内容，但没有再次执行 `myagents task get`。 |
| N3 微信配对未完成时显示运行中 | 中 | 新助理添加微信，等待二维码自动刷新次数耗尽后关闭扫码页。设置仍显示 Running，底层频道为启用且标记为已完成设置，账号 ID 和配对凭据均缺失，且没有测试私聊进站。 |
| N4 全量脚本仍存在平台或夹具失败 | 低 | 用 `core.autocrlf=true` 检出，准备依赖并启用 Windows Python UTF-8，再执行 `node --test scripts/*.test.mjs`。仍有 16 项失败，涉及 Windows 路径拼接、跨平台资源或包夹具。已单独验证 D6 的记忆测试；Linux 对照结果见 R3。 |

## 证据

### R1

- 原版 `section_edit.py` 上用两个独立进程对同一文件、同一基线同步启动八轮。八轮均恰有一个退出 0、一个以 `FILE_CHANGED` 退出 2。失败方使用 `--show` 重读后重试，八轮都保留两条记录。目录无残留锁。普通基线 `2c014d826d51…`，一个胜方组合重试后为 `ccd306cd404d…`。
- 预建两分钟前的锁，单进程在 0.18 秒后成功并清除锁。预建刚创建的锁，单进程 15.18 秒后以 `LOCK_BUSY` 退出 2，文件摘要保持 `68616107ced0…`，原锁仍在。
- 将过期锁和并发组合，两个原版进程在第 7 轮均退出 0。基线 `5d262b06d399954367dd43a31d6bc2d9fb88ba93c877b15a1fe736f1a3ec750f`。两个进程各自报告 `266e1ddc5f4bc6474c625e1e10c7b683e71fccf998818a93df43e60daab4d4f6` 与 `a0ae71761e672cd039cbdcf2e581e2141c5be463cb56e357d66ddd68e7dc63f1`。磁盘为后者，只有后者的记录。这次验证用外部探针同步起跑，两个进程都执行原版脚本。
